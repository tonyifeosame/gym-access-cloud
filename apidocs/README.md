# AccessLink API documentation — `https://accesslink.store/docs`

The public reference for the AccessLink API: a concise, integration-focused
guide (quick start, authentication, working `curl` examples, fingerprint
authentication, errors, rate limits) followed by the full reference — the
public API v1 in full, and the small slice of the console API that fingerprint
enrolment needs, clearly marked. Rendered with
[Scalar](https://github.com/scalar/scalar) from one OpenAPI document, and
served from the AccessLink Console's own domain under `/docs`.

## Where the source lives

| What | Where |
|---|---|
| **The OpenAPI document — the single source of truth for the site** | `apidocs/openapi.yaml` (guide = `info.description`, reference = `paths`, error pages = `x-accesslink-error-codes`) |
| The page that mounts the reference | `apidocs/index.html`, `apidocs/src/main.ts`, `apidocs/src/theme.css` |
| Build configuration (Vite, `base: /docs/`) | `apidocs/vite.config.mjs` |
| Document validation | `apidocs/scripts/validate.mjs` (OpenAPI 3.1 + house rules) and `apidocs/scripts/validate-examples.mjs` (every example against its schema) |
| Router parity and example replay | `openapi_docs_test.go` in the Go module |
| Error-code pages (`/docs/errors/<code>`) | generated by `apidocs/scripts/build-errors.mjs` |
| Browser render check | `apidocs/scripts/check-site.mjs` |
| Publishing into the console's build | `web/scripts/build-docs.mjs`, run as the console's `postbuild` hook |

There is no page content outside `openapi.yaml`. Change the document, rebuild,
and everything follows.

## How the site is served

`https://accesslink.store` is the AccessLink Console — a Render static site.
The console's build (`npm run build` in `web/`) ends with a `postbuild` step
that builds this directory with Vite `base: /docs/` and copies the result to
`web/dist/docs/`. Render serves a file that exists before it applies any
rewrite rule, so `/docs/…` are answered as files and the console's SPA
rewrite (`/*` → `/index.html`) never sees them; a bare `/docs` is redirected to
`/docs/` by a rule in `render.yaml`. No login is involved — the docs are plain
static files on the same origin — and the console service's response headers,
including its Content-Security-Policy, apply to them unchanged.

Published paths:

- `/docs/` — the reference (hash navigation, e.g. `/docs/#description/quick-start`)
- `/docs/openapi.yaml` and `/docs/openapi.json` — the document, for tooling
- `/docs/errors/<code>` (and `/docs/errors/<code>/`) — one page per error code, the
  `doc_url` the API puts in every public error body (`models.APIErrorDocBase`)
- `/docs/sitemap.txt`

## Running locally

```bash
cd apidocs
npm ci
npm run dev          # http://localhost:5175/docs/ — edits to openapi.yaml reload
```

## Building and checking

```bash
cd apidocs
npm run validate     # the document and every example, in a few seconds
npm run build        # validate → vite build → error pages; output in dist/
npm run check        # dist/ mounted at /docs/ behind a console-style fallback, in Chrome
npm test             # all three
```

To check the exact artefact the console ships:

```bash
cd web && npm run build            # produces web/dist/docs via postbuild
cd ../apidocs && DOCS_SITE_ROOT=../web/dist npm run check
```

And the parity tests against the real router, from the repository root:

```bash
go test -run 'TestOpenAPI' .
```

## What keeps it honest

- **Every documented route is mounted; every mounted `/api/public/` route is
  documented** (`openapi_docs_test.go`, against `NewRouter()`).
- **The error catalogue equals the server's** — code, type, status and message —
  and `models.APIErrorDocBase` is the page base the site generates.
- **Every example validates against its schema** (request bodies, responses,
  parameters, component examples) and **every `curl` in the guide is real**:
  tagged fences (` ```bash {op=createMember} `, ` ```json {op=createMember status=201} `)
  are checked for the production origin, the operation's method and path,
  documented query parameters, the `<ACCESSLINK_API_KEY>` placeholder and a
  schema-valid body — then replayed through the real router by
  `TestOpenAPIGuideExamplesRunAgainstTheRouter`, which asserts the documented
  status and response keys (including the `401` and `409` examples).
- **House rules:** guide sections in the required order (Quick start →
  Authentication → Integration flow → Core operations → Fingerprint
  authentication → Errors → Rate limits → Full API reference); no internal
  implementation language; no hosting hostname, credential value, biometric
  field, device/site-key route or replication claim anywhere in the document.
- **The render check** opens the build in the locally installed Chrome, mounted
  at `/docs/` behind a console-style SPA fallback and under the console's CSP
  from `render.yaml`, and checks: `/docs` and `/docs/` reach the reference (not
  the console), every section and operation renders, the collapsible reference
  notes are real `<details>`, all sidebar links resolve, search works (button
  and `Ctrl+K`), keyboard focus is visible, contrast ≥ 4.5:1, no overflow at
  390 px, no console errors, **no request leaves the origin**, and every
  `/docs/errors/<code>` answers with and without a trailing slash.

## Design decisions

- **No third-party requests.** Scalar is bundled from npm; its fonts, telemetry,
  request proxy, "Agent" chat, "Generate MCP" and developer toolbar are all
  off (`src/main.ts`). The render check fails if the page requests any other host.
- **"Try it" is off.** The in-page client would send a reader's real key through
  `proxy.scalar.com` (or require CORS changes on the API). The page offers
  generated request samples in a dozen languages with `<ACCESSLINK_API_KEY>`
  instead. To enable the client later: add the docs origin to the API's
  `CORS_ALLOWED_ORIGINS`, keep `proxyUrl: ''`, and set
  `hideClientButton` / `hideTestRequestButton` to false.
- **Console endpoints are a separate tag group** with their own security scheme
  and error shape, and the guide says they carry a weaker compatibility promise.

## Deployment

Nothing separate: the console service (`accesslink-console`, root `web`,
build `npm ci && npm run build`, publish `dist`) produces `/docs` as part of
its normal build, so **deploying the console deploys the docs**. The API's
`doc_url` base moved with the site, so the API is deployed as well for new
error bodies to link to the new pages.

`docs.accesslink.store` (the `accesslink-docs` service) is retiring: it now
only redirects every path to the same path under `https://accesslink.store/docs`
so that previously emitted `doc_url`s and bookmarks still land. Once the API
deploy is live and the redirect has served for a while, delete the service, the
`docs.accesslink.store` CNAME and its block in `render.yaml`.
