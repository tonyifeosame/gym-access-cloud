# AccessLink API documentation — `docs.accesslink.store`

The public reference for the AccessLink API: the public API v1 (integration
credentials) in full, and the slice of the console API that fingerprint
enrolment needs, clearly marked as such. Rendered with
[Scalar](https://github.com/scalar/scalar) from one OpenAPI document.

## Where the source lives

| What | Where |
|---|---|
| **The OpenAPI document — the single source of truth for the site** | `apidocs/openapi.yaml` |
| The page that mounts the reference | `apidocs/index.html`, `apidocs/src/main.ts`, `apidocs/src/theme.css` |
| Validation of the document | `apidocs/scripts/validate.mjs` (OpenAPI 3.1 + house rules) and `openapi_docs_test.go` in the Go module (route and error-code parity with the server) |
| Error-code pages (`/errors/<code>`) | generated by `apidocs/scripts/build-errors.mjs` from `x-accesslink-error-codes` in the document |
| Browser render check | `apidocs/scripts/check-site.mjs` |

There is no hand-written page content outside `openapi.yaml`: the guide
sections (Getting started, Authentication, Fingerprint authentication,
Pagination, Idempotency, Errors, Rate limits, Changelog) are the document's
`info.description`, the reference is its `paths`, and the error pages are its
`x-accesslink-error-codes`. Change the document, rebuild, and everything
follows.

## What keeps it honest

- `openapi_docs_test.go` (run with the rest of the Go suite) holds the document
  to the router: **every documented route must be mounted** with that method
  at that path, **every mounted `/api/public/` route must be documented**, the
  error catalogue must equal `models.APIErrors` code for code (type, status,
  message), and the document must never name a device or site-key route, a
  credential shape, a biometric field, or a replication claim.
- `scripts/validate.mjs` checks the document is valid OpenAPI 3.1 with every
  `$ref` resolvable, and applies the house rules: every operation has exactly
  one tag from a declared tag group, a summary, description, operationId and
  a 2xx response; public routes declare `IntegrationCredential`, name their
  `x-scope`, and document 401/403/429/503; console writes require the
  `X-CSRF-Token` header; every `doc_url` and example code is registered; the
  document contains no credential values, no development URLs and no
  replication claim.
- `scripts/check-site.mjs` opens the built site in the locally installed
  Chrome and checks that every guide section and operation renders, every
  sidebar link resolves, search opens (button and `Ctrl+K`) and finds an
  endpoint, Tab lands on a control with a visible focus ring, body-text
  contrast is at least 4.5:1, a 390 px viewport has no horizontal overflow,
  there are no console errors, **no request leaves the site's own origin**,
  and `/openapi.yaml`, `/openapi.json`, `/errors/` and every
  `/errors/<code>` (with and without a trailing slash) answer.

## Running locally

```bash
cd apidocs
npm ci
npm run dev          # http://localhost:5175 — edits to openapi.yaml reload
```

## Building and checking

```bash
cd apidocs
npm run validate     # the document alone, in under a second
npm run build        # validate → vite build → error pages; output in dist/
npm run check        # opens dist/ in Chrome and runs the render check
npm test             # all three, in that order
```

And from the repository root, the parity tests against the real router:

```bash
go test -run 'TestOpenAPI' .
```

The build emits `dist/index.html` (the reference), `dist/openapi.yaml` and
`dist/openapi.json` (the document, for download and for tooling),
`dist/errors/index.html` and one page per error code in both
`errors/<code>/index.html` and `errors/<code>.html` form, `dist/sitemap.txt`
and `dist/robots.txt`.

## Design decisions worth knowing

- **No third-party requests.** Scalar is bundled from npm rather than loaded
  from a CDN; its fonts, telemetry, request proxy, "Agent" chat and
  "Generate MCP" button are all switched off in `src/main.ts`. The render
  check fails if the page requests any host but its own.
- **"Try it" is off.** Scalar's in-page client would send a reader's real
  `atp_live_` key through `proxy.scalar.com`, or need the API to allow
  `docs.accesslink.store` for CORS (`CORS_ALLOWED_ORIGINS`, a production
  setting). Neither is acceptable for a public page, so the site shows
  generated request samples (curl by default, a dozen other languages a click
  away) with the placeholder `atp_live_<your-key>` instead. To enable the
  client later: add the docs origin to the API's `CORS_ALLOWED_ORIGINS`, keep
  `proxyUrl: ''`, and set `hideClientButton`/`hideTestRequestButton` to false.
- **Error pages match `doc_url` exactly.** The API emits
  `https://docs.accesslink.store/errors/<code>` (no trailing slash) on every
  public error; the site serves that URL, and the slash form, for every code
  the server knows.
- **Console endpoints are a separate tag group** ("Console API (operator
  session)") with their own security scheme and error shape, and the guide
  says plainly that they carry a weaker compatibility promise than the public
  tree.

## Deployment

A **Render static site** — the same arrangement as the console, no backend:

| Setting | Value |
|---|---|
| Service type | Static Site |
| Name | `accesslink-docs` |
| Repository / branch | this repository, `main` |
| Root directory | `apidocs` |
| Build command | `npm ci && npm run build` |
| Publish directory | `dist` |
| Auto-deploy | as the other services (see `render.yaml`; the dashboard governs) |
| Custom domain | `docs.accesslink.store` |
| Headers | the CSP and hardening headers listed in `render.yaml` under `accesslink-docs` |

The service block is in `render.yaml`. Creating it is a deliberate dashboard
action (Blueprint sync or *New → Static Site*), not something a push does.

**Steps, in order:**

1. Merge the branch that adds `apidocs/` to `main`.
2. Render dashboard → *New → Static Site* (or sync the Blueprint) with the
   settings above. Wait for the first build; the site is live at the
   `*.onrender.com` hostname Render assigns.
3. Open it, confirm `/` renders and `/errors/resource_not_found` answers.
4. Render → the service → *Settings → Custom Domains → Add* `docs.accesslink.store`.
   Render shows the hostname to point at and issues the TLS certificate once
   DNS resolves.
5. Add the DNS record (below), wait for the certificate, then confirm
   `https://docs.accesslink.store/` and an error page.

Nothing in the API or the console changes; the API already links to
`docs.accesslink.store/errors/<code>` and simply starts resolving.

## DNS

At the `accesslink.store` DNS provider:

```
docs.accesslink.store.   CNAME   <the accesslink-docs service>.onrender.com.
```

(the exact target is shown on the custom-domain screen; it is the service's
Render hostname). Nothing else: the site is static, has no API of its own, and
needs no record for `www`.
